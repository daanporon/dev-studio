# Scripts reference

Every script, reconciler, table and event of dev-studio, in detail. `AGENTS.md` keeps only an index of the entry points a role calls by hand; this page holds the rest, moved from AGENTS.md's old `## Scripts` section word for word and in the same order.

**A unit documents its scripts, tables and events here, not in `AGENTS.md`.** `AGENTS.md` takes at most one index line for a new entry point a role calls.

## Scripts

- `bin/role/squad-state.sh` — read/write a squad's state file; `register-plan` or `add-unit` of open work on a `done` squad sets it back to `running`. `register-plan` takes only `<file> <plan>`: any further argument (`--dry-run` too) exits 2 and writes nothing. `tests/squad-state.sh` verifies it. A feature squad's `set-status done` (debrief-in-needs-you U1) also needs its Try it page, `state/<label>/squads/<topic>-try-it.md` (the Thinker keeps it current, `roles/thinker.md`): it refuses with the page's path when the file is missing, or, on the loop's store, older than the last `unit_done` event; a squad file outside `squads/` or with no done unit skips the check. Archive moves the page to `archive/` (`fulfil/squad.ts`); the board's squad `try_it` `{name, markdown, mtime}` (`board-data.ts` `tryIt`, live and archived) shows as Documents → Try it, and `briefing-input` counts its numbered steps (`tryItPage`) before the debrief and plan. On the loop's store `set-unit-status <slug> done` refuses a unit whose recorded PR the loop has not observed `MERGED` (open, closed or unread; `--no-pr` does not skip it), so its Builder stays until the merge, when the loop marks it done and retires the Builder (`tests/close-role.sh`). `revoke-plan <plan> --why <text> [--keep-started]` (hold-cancels-queue-undo-approval U2) takes a plan approval back: out of `approved_plans` into `revoked_plans`, the approved copy moved to `<plan>.revoked-<stamp>.md`, the plan's queued Builders dropped in the same write, its started ones paused on a `plan` prerequisite (`bin/loop/pause/pause.ts`) that `approve-plan` of it releases (`reconcilers/dependency-waits.ts`), one line per unit and one message to the Lead; whether a plan counts as approved is `bin/loop/squad/plan-approved.ts`. The board does it from the squad box's Plans list (hold-cancels-queue-undo-approval U3): an approved plan (`approved`, `revoked_at`, `queued`, `started` in `board.json` `plans`) shows an `approved` chip and a ⋯ **Take back approval** that asks for a why and posts `/api/plan {project, topic, plan, why, keep_started?}` (409 for another squad's plan, an unapproved one or a second pending); one `plan-revoke` request, run by `bin/loop/fulfil/plan-revoke.ts` as the command above. `tests/loop/revoke-plan.test.ts`, `tests/loop/fulfil-plan-revoke.test.ts`, `tests/board-serve.sh`, `tests/loop/board-render.test.ts`.
- `bin/commands/spawn-squad.sh` — ask the loop for a squad: writes the squad wish (`ds want`), and the loop makes the Run, task, Lead and role children (U158; `--framing-file <path>` reads the brief from a file, exclusive with `--framing`); roster from `conventions/roles.conf`.
- `bin/commands/add-role.sh` — ask the loop to add one role worker to a running squad: a wish writer (`ds request`); the loop picks and starts it. `--host <name>` (side-loop-host U10) puts it on that side host (`conventions/backend.md`, "A backend on another host"); a host not in `ds host list` is refused.
- `bin/ds pick <project> <role> [--tier t] [--phase p] [--agent a] [--model m] [--effort e] [--account id]` — the loop's picker (`bin/loop/capacity/pick.ts`) and the only one: the role's model on the account that resets soonest with room (rows in `loop.db`), then its `roles.conf` fallbacks, else `WAIT <epoch>` (exit 3); each call records a `pick` event. With `builder_host_brake on` a new Builder start waits `WAIT host: …` while the host crosses a `machine_*_crit` line (levels from `bin/loop/capacity/machine-level.ts`, shared with the board's machine panel; `tests/loop/host-brake.test.ts`). For the board, read-only (board-shows-host-brake U1): `slot.ts` `seats()` gives each live Builder seat with why it is held (`liveWhy`: starting, pausing, restarting, working, idle), the `ds pick` holds and the seats used per lane, as `slot()` counts them; `seatable()` gives the queued units the same seat walk would start now (less a planned unit whose Builder is live and a Builder waiting on an account); `pick.ts` `brakeView()` gives the host's sample state, the crit line it crosses (`hostCritHit`, which `hostCrit` formats) and every project's `builder_host_brake` (`tests/loop/slot-seats.test.ts`). The board reads them (board-shows-host-brake U2): `board-data.ts` `headerSummary` takes the Builders tile from `seats()` (`builders_normal`, `builders_light`, `builders_total`, `builders_left`, `builders_over` and `builders_seats` `{used, total, by_why, list}`, every live Builder in any squad, not only the working ones of active squads) and `brakeOf` gives header `brake` `{setting, sample, hit, on, projects, holding, held, free}` (also `flow.brake`) while the host sample crosses a crit line; `held` is `seatable()`'s count. `flow.ts` `queuedGroup` puts a `WAIT host:` pick in `waiting for the host`; the text board prints a `BUILDERS` line whenever `max_builders` is set and a `BRAKE` line (`brakeText`); `web/board.html` shows the red `⛔ host brake` tile and the queued banner (`BrakeBanner`) (`tests/loop/board-seats-brake.test.ts`). the loop's start fulfillers call it (spawn-squad only writes a wish). `tests/loop/pick.test.ts` and `tests/start-pick.sh` cover it.
- `bin/loop/capacity/walk-memo.ts` (loop-tick-8s U3) — the picker reads its per-tick facts once: `picks.ts` runs its walk inside `withWalkMemo(store, now, …)`, in which `memo(store, now, kind, key, read)` keeps each fact `slot()` and `pick()` read (a Builder's lock, pause and presence, the reservations, holds, asks, units and lanes, the limits rows, the machine sample) for the rest of the walk, while the start slots this walk gives (`picks.slot = 1`, read live between `liveWhy`'s two kept halves) and the account loads stay live, so a later pick sees a seat an earlier one took. `decide()` runs inside `withDecideMemo`, which keeps only the facts no decide writes (`STABLE`: limits rows, the machine sample, `liveness.ts` `openCalls`, each worktree's parsed transcript tail), since `look()` writes member and episode rows. A scope belongs to one store and one `now`; outside a scope (the board, `ds pick`, `fulfil/member.ts`, `ready.ts`) `memo()` just reads; `DS_PICK_MEMO=0` turns both off. `tests/loop/slot-memo.test.ts` compares the picks, `slot()` and `decide()` with and without it.
- `bin/loop/settings/roster.ts` (U267) — the one roster rule: `effectiveRoster` gives a project's roles.conf rows over the default's, per role (a role the project lacks runs the default row). `pick.ts`, `fulfil/squad.ts` and `settings.ts` read it; `roles.sh` (`rosterLines`, through `bin/lib/settings-rows.ts`, U256), `spawn-squad`, `review-unit` (`effectiveRosterRows`) and `roleRow` (`bin/lib/lib.ts`, through `settings.ts` `readRoster`, U257) apply the same overlay to the rows. `set` writes one role's row; `reset`/`rm` drop it. `tests/roles.sh`, `tests/loop/pick.test.ts`, `tests/loop/settings.test.ts`.
- `bin/loop/settings/settings.ts` (U255) — the one writer of a project's settings rows (`config` rows of `limits.conf`, `roles.conf`, `models.conf`, `ship-mode`): get (env > project > default, with the source), set, rm and reset with the shell scripts' checks (a known limits key and value shape, shared with `limits-ts.ts` through `limitValueProblem`; a known role; a catalog model; a known ship mode), each change one `config_history` row (migration 0040) and a rewrite of the backup `state/<label>/settings.export`, which nothing reads. `ds config get|set|rm|reset|export|history|import|copy|prune` call it (`copy <from> <to>` is the checked copy through `planImport`/`applyImport`, `import --dry-run` previews a restore, `prune` drops rows of keys this dev-studio doesn't know, and `export` starts with the `#! ds-settings` file header; `tests/loop/config-copy-cli.test.ts`), and so do `limits.sh`, `roles.sh`, `ship-mode.sh` and the board's Settings edits (`bin/loop/fulfil/config.ts`). The board's Settings and Roles tabs show each override's last change from `config_history` (`changed` on `/api/limits` and `/api/roles`: who, when, imported) with an **undo** button: `POST {undo: <history id>}` files a `config-undo` request that puts the key back to what that change replaced through `settings.ts`, leaving a history row of its own (a newer change refuses it; an import has no undo). Import and Export on the board's Settings window (settings-export-import U3): `GET /api/settings-export?project=` (the export text, transfer header first), `GET /api/settings-import?project=` (the other projects), `POST /api/settings-import/preview {project, text|from}` (`planImport` with `board: true`, reads only, 400 naming why for a text that is no export) and `POST /api/settings-import {project, text|from, picks: [{file, key, expect}]}` (one `settings-import` request that `bin/loop/fulfil/config.ts` runs through `applyImport` as `board`, result `written`/`skipped`/`stale`); `tests/loop/board-settings-import.test.ts`, `tests/board-serve.sh`. Readers outside the loop use its read API (U257): `readGet`, `readRows`, `readRoster` and `readProjectRosterLines` open the state root's `loop.db` read-only (`settingsAt()` in `bin/lib/shared.ts` gives the root and the shipped conventions, DS_ROOT honored) and fall back to the shipped defaults when there is none; review-unit's roster and limits, spawn-squad, up, install and `roleRow(<label>, <role>)` read through it, and `dsLimit`, `limitSrc`, `shipMode` and `roles.sh` through `bin/lib/settings-rows.ts` (U256), never `state/<label>/*.conf`; `tests/loop/settings-files-guard.test.ts` fails on any code under `bin/` that builds a project settings-file path outside the importer, the config observer, `settings.ts` and the cut-over. Since the cut-over (U256, `bin/loop/settings/settings-migrate.ts`) the rows are the only copy: once per state root (the config observer's tick, `migrate-host`, or a CLI write through `openSettings`) each `state/<label>/{limits,roles,models}.conf` and `ship-mode` becomes rows (history actor `migration`) and is renamed `<file>.imported-<date>`, the export is written and the mark `state/.settings-migrated` comes last (`bin/loop/settings/settings-mark.ts`; `DS_SETTINGS_CRASH=<step>` stops after a step for tests). After it the observer reads only `conventions/` and drops no project's rows, a file that reappears is not read and raises one Studio alert (`bin/loop/reconcilers/settings-files.ts`), and `ds config import --project <p> <path>` (an export or one file) is the only way back in. `docs/settings.md`. `tests/loop/settings.test.ts` and `tests/loop/settings-migrate.test.ts` cover it.
- `bin/loop/capacity/credits-card.ts` (provider-billing-fallback U4) — the Needs-you card for an account out of credits: per live credits hold (`bin/loop/capacity/credits.ts`) with a member the picker cannot move (or pinned), one `out_of_credits` alert naming the notice, the billing link, who is stuck and the answers **Fixed** (re-enable, hold cleared) / **Switch it off** (`bin/loop/fulfil/studio.ts`); it clears when the hold ends or nobody is stuck, and a `credits_moved` note says where everyone went. Run by the limits reconciler; the board's Accounts row reads `out of credits · <link>`. `tests/loop/credits-card.test.ts`, `tests/board.sh`.
- `bin/loop/capacity/login.ts` (claude-login-ended U2) — an account whose Claude login ended, held host-wide like credits: the usage probe's `login ended` note (`probeLogin`, beside `probeCredits`) or Claude's `● … · Please run /login` line on a member's screen (`fingerprints.ts` `CLAUDE_LOGIN_RE`, kind `login`: read at once, no dialog, a later entry ends it) writes one episode `{project '', subject login|<agent>/<account>, kind account}` (one `account_login_ended` event, `from` screen|probe), renewed to now + 1 h while either stands. `pick.ts` leaves the account out (block `login`, a wait names `<agent>:<account> login ended`); every member on it, the Studio too (`Studio's login ended`), reads limited with no reset (`limits.ts` `loginOf`) and moves like a limited one, with no "carry on" while held. An allowance from the probe, `ds account enable` or `ds limit-lift` ends it (`clearLogin`: account lifted, member episodes `cleared`, one `account_login_cleared` event with `by`); after an operator clear only a probe reading taken later (its `updated`) holds again, and each member still on the account gets one `login-ok` tell ("your account's login works again"). `tests/loop/login.test.ts`.
  The board (claude-login-ended U4): `board-data.ts` `accounts()` adds `login` `{until, notice, where}` from `liveLoginHolds` (as `credits` from `liveHolds`); the row text reads `<name> login ended · run /login` with no percentages, `accountsSummary` counts it as not free (`login` list, level warn) and the tile detail reads `<label> login ended`; `web/board.html` shows a `login ended` badge and line. `tests/board.sh`.
- `bin/loop/capacity/login-card.ts` (claude-login-ended U3) — the Needs-you card for a held login, run by the limits reconciler beside `creditsCards`: per live login hold with a member of the project on it (the Studio too), one `alert` `login.card|<agent>/<account>`, kind `login_ended` (Needs-you at once, no grace), titled `<label>: login ended`, naming where to run `/login` (the Studio's terminal, else the first stuck member's), the command (`claude /login`, `CLAUDE_CONFIG_DIR=<dir> claude /login` from the probe note's tail, else "with that account's config dir") and every member on it, the ones the picker cannot move first and marked. A moved member keeps the card; it clears when the hold ends or nobody is left (then one `login_moved` note). Answers in `fulfil/studio.ts` dismiss: **Logged in** (`clearLogin`, by `board`) and **Switch it off** (`setAccountEnabled` false). `tests/loop/login-card.test.ts`, `tests/loop/fulfil-board.test.ts`, `tests/loop/card-place.test.ts`, `tests/board.sh`.
- `bin/loop/squad/member-ready.ts` + `bin/loop/fulfil/chat.ts` (board chat U2) — `memberReady(store, project, wt, now, {quietS, handle?, agent?, before?, screenNoise?})` is the one guard before the loop types into a member's terminal: not working (a Claude member Orca still reads `working` after an Esc counts as not working when its transcript's last turn ended or was interrupted, liveness `turnEnded`, and the screen read since its output shows an empty prompt and no `esc to interrupt`; studio-hung-agent-broken U4), output and transcript quiet for `quietS`, the screen read since that output with an empty prompt (`promptDraft`), no open picker (an open question with a `tool_use_id` for it, or a menu its driver's `answerMenu` knows), no unread mail, no earlier undone answer/poke/keys/chat request or accepted delivery for it; each refusal names its why. `studioReady()` is it on the Studio's adopted handle (quiet 120 s) plus the Studio's own checks. A `chat` request (`{text, via?, files?}`, at most 2000 characters of text, line breaks and tabs allowed since U19) is typed as `dev-studio board, the operator says: <text>` once its member is ready, oldest first, never while paused; until then its `result` is `{state: "queued", why, since?}` (rewritten only when the why changes), then `{ok: true, state: "turn started"|"sent", delivered, delivery}`, or after `chat_queue_min` (30) of waiting on the member itself (not on a pause or an earlier chat) `{ok: false, error: "never ready: <why>"}`. `files` (chat-image-upload U2) are at most 4 stored file names (`bin/loop/chat/files.ts`: `CHAT_FILE_NAME`, `chatFileKind`, `chatFilePath` into `<root>/<label>/chat-files/<topic>/`; the text may then be empty): the typed line ends ` [images attached; open each with your file-reading tool: <abs path>, …]` for images, then ` [files attached; read each with your file-reading tool: <abs path>, …]` (`FILES_MARK`) for text files and PDFs (markdown-file-upload-support U1), and a missing file, a bad name or over 4 fails the request and types nothing (`tests/loop/chat-files.test.ts`). Members, the Studio too, are ready after `chat_quiet_s` (10) of quiet; for a Claude member (studio-chat-queued-busy U3) the chat passes `screenNoise: "ignore"`, so output alone does not hold it: only a transcript written within `chat_quiet_s` or `esc to interrupt` in the last rows of a screen read since the output (`workingOnScreen`, why `busy: working on screen`), while every other caller and agent keeps the output window (`tests/fixtures/member-ready/`); a send that fails rewrites the result to `{state: "queued", why: "send failed[: <err>]", failing: true, since}` (the Studio keeps the error text) and counts in the member's `send-fail` episode (`bin/loop/squad/send-fail.ts`), whose third failure in a row raises one `sweep-send-fail.<member>-<n>` card (`reconcilers/send-fail.ts`) that `alertGone` clears on the next good send; the Orca observer re-reads the screen of a member with a queued chat once its output settles. An accepted send is a `chat` delivery: verified when a turn starts, else one "Chat not taken" alert after 60 s, never resent. A waiting chat has **Cancel** and **Send now** (studio-chat-queued-busy U4; `POST /api/chat-cancel` and `/api/chat-now {project, id}`, 409 once typed, kinds `chat-cancel` and `chat-now` run by this fulfiller and allowed while paused): cancel ends it `{ok: false, state: "cancelled"}`, now sets `now: true` in its payload so the readiness check runs with `quietS: 0` (the screen read, empty prompt, picker, menu, working and earlier-request checks stay); `chatJson` sends carry `age_s`, `failing`, `now`, `first` (the member's oldest queued send, the only one Send now applies to) and `gives_up_at` (`since` + `chat_queue_min`, null while no clock runs). One count rule (chat-multiline-send-fails U2, `bin/loop/chat/limits.ts`): the limit counts code points of the text after CR LF/CR → LF and trim, and the page counter (`N left` / `N over`, Send refuses locally), `POST /api/chat` (400) and the fulfiller share the error texts `a chat is at most 2000 characters; this one has N` and `a chat may hold line breaks and tabs, but no other control character (line L)`. A failed or cancelled send has **Edit** (its text and images back in the member's box) and **Dismiss** (`POST /api/chat-dismiss {project, id}` → one `chat-dismiss` request, 409 for a still-queued send, allowed while paused; the fulfiller writes `dismissed_at` into the send's result and `chatJson` leaves it out). A chat to a non-hub member appends `- <iso> operator → <topic>/<role[-suffix]>: <text>` to `state/<label>/crew-chat.md`, which the squad Lead's watch tick lists under `CREW CHAT:` (last 24 h, at most 10) — no mail. `tests/loop/member-ready.test.ts`, `tests/loop/fulfil-chat.test.ts`, `tests/watch.sh`.
- `bin/loop/chat/keys.ts` + `bin/loop/fulfil/keys.ts` (board chat U19) — multi-line chat, keys and a live screen from the board's Chat panel. A chat may span lines (the page keeps `\n` and tabs, CR LF read as LF; `fulfil/chat.ts` refuses any other control character; each backend pastes it whole, and `chat/turns.ts` `textTurn` reads a `<pasted_content>`-wrapped board line as the operator's turn; the crew-chat.md line joins the lines with ` ↵ `). `POST /api/keys {project, topic, wt, keys}` files one `keys` request `{keys, via: "board"}`: 1 to `KEYS_MAX` (8) of `contract.ts` `KEYS` (Escape, Up, Down, Enter, Tab, …) or one digit or lowercase letter, no Enter added (400 otherwise, 404 for no live member, 409 while paused or with a press of that member still open). The fulfiller presses them with `memberReady(…, {interrupt: true})`, which needs only a live terminal (so an Escape reaches a working member), through the member's driver (`Driver.keys`, `keysVia`: Orca's adapter `keys` with the bytes of `keyBytes`, a contract squad's `terminal.send {keys}`) or the Studio's adopted handle; one try, a press older than `KEYS_STALE_S` (60) fails `not pressed: filed N s ago` (a paused member's press is held and goes stale); result `{ok: true, state: "sent", keys}` or `{ok: false, error}`. `chatJson` adds `screen` `{tail, at, age_s}` (the member's newest screen read, the Studio's from its adopted terminal), and the Orca observer re-reads, at most every 3 s once its output moved, the screen of a member with a press in the last minute or a `screen`-source chat row. The page (chat-key-buttons U1): the compose box is one rounded card (`chat-card`: the text on top, then 📎 and a round amber ↑ Send, a red round **■ Stop** before Send while the member works, a `api/keys` Escape post); Chat shows no key row; a menu on the member's screen (`screen.menu > 0`) or an open board question for the member shows as a one-line banner that opens the Question view (U2, below); under Screen the key row above the card always shows Esc ↑ ↓ ⏎ ⇥ and the menu digits 1-5, each a `api/keys` post; a member with no transcript opens on its live screen (`chat-screen`, `read N s ago`), and any member with a screen read has a Screen/Chat toggle in the panel header, before ✕. The Question view (chat-key-buttons U2): `chatJson` adds `questions` (`board-data.ts` `chatQuestions`: the open questions whose card opens a chat with this member by the `chat_wt` rule, each `{id, title, question, choices, since, source, answerable}`, `answerable` false for a terminal-only picker) and `screen.prompt` / `screen.options` (`menuText`: up to 4 lines above the last numbered run with a selection marker, and its labels, marker and number stripped; a plain numbered list gives none); `chatCrew` rows carry `asks`. A member with a menu or open question gets a Question · Chat · Screen control; a blocking item opens the view once per id+since (or menu prompt), several page `1 of N ‹ ›` (screen menu, then blocking, then oldest); a choice answers through `sendAnswer(…, since)`, a terminal-only picker offers `Open Screen to answer`, a menu with no board question shows one ≥44 px button per option pressing its digit through `api/keys`; after an answer or press the panel returns to Chat; a `?` marks the member in the switcher and tabs. `tests/loop/chat-questions.test.ts`. `tests/loop/fulfil-chat.test.ts` ("board keys"), `tests/loop/member-ready.test.ts`, `tests/loop/board-chat-page.test.ts`, `tests/loop/chat-tail.test.ts`, `tests/board-serve.sh`, `tests/board-page.sh`.
- `bin/loop/fulfil/account-reset.ts` (account-free-resets U4) — the board's **Use** button on a free reset grant: `POST /api/account-reset {project, agent, account, grant}` takes only a grant the stored resets list as `usable_now`, refuses a second press while one is open (409) and adds the idempotency key; the fulfiller is the only caller of the backend's `account-reset-use` (in the background), passes the same key on every retry (no answer is retried, never re-claimed), finishes the request with the outcome (`used`, `nothing_to_reset`, `no_grant`, `already_used`, `failed`), logs `account_reset_used` and forces one accounts refresh; the board shows the last press of the hour (`reset_last`) under the cell. - `bin/commands/close-squad.sh` — ask the loop to close a squad (a wish writer, U158): the loop removes its recorded worktrees, moves its state file and plans to `state/<label>/archive/` and keeps unmerged branches. It drops the squad's open questions (morning-brief-stale-items U2; `drop` in `bin/loop/messages/questions.ts`): each `questions` row reads `status = 'dropped'` (reason `squad archived` in `answer`, `answered_via = 'archive'`, one `question_dropped` event; never `answered`, never deleted), the archived JSON keeps them under `dropped_questions` with an empty `waiting_on_you`, and the row's doc loses its queue in the same `wish_done` write so no later sync reopens them; when one was blocking, one Needs-you card `Archived with a blocking question open: <topic>` (kind `questions_dropped`, option **Seen**) names each by title and asker. Migration `0053-orphan-questions.sql` dropped the open questions already left on closed squads the same way (`squad archived (cleanup)`, no card). It also clears the squad's Studio cards (`archivedCard` in `bin/loop/reconcilers/alerts.ts`, `alertGone`: a card naming the squad whose newest row reads `closed`, or wants `gone` with a `done…` result, is gone, "its squad was archived"), except its `sweep-debrief-<topic>-…` card, a `questions_dropped` card and a `Stop command failed` card. A worktree removal `fulfil/close.ts` drops as stale (Orca still lists the stopped agent's dispatch) is tried again under a new episode (`close-drift.ts` `removeRetry`: 6, 12, 24, then every 30 min, no cap), and from the third drop one `Archive slow: <topic>` card (kind `archive_slow`) stands until the worktree is gone (`tests/loop/close-remove-retry.test.ts`). The board says what an archiving squad waits on (archive-stuck-worktrees U2; `board-data.ts` `archiveWaits`, inside `phaseFact`'s `phase.note`, also the text board): per member with a worktree `waiting on <role[-suffix]>: stopping | removing the worktree | removal skipped (<reason>) <m> min ago, try <k>, next in <t> | kept as a leftover: <why> | waiting for a stop` from its newest `action:member.close` episode, and the `stuck` clock runs from the newest of the wish, the debrief step's end and the last `member_closed`/`leftover_recorded` event. `tests/board.sh`. `tests/loop/archive-questions.test.ts`, `tests/loop/needs-clear.test.ts`.
- `bin/loop/reconcilers/alerts.ts` (`permissionScreens`) + `bin/loop/chat/menu.ts` (permission-prompt-needs-you U3) — the screen check for a permission prompt the hook missed. `menu.ts` holds the numbered-menu scan the board chat already used (`menuText`, `menuOptions`) and `permissionMenu`: that menu under Claude's "Do you want to …?" line, or under Codex's "Would you like to run the following command? / make the following edits? / grant these permissions? / send input to terminal …" (looked for up to 15 lines above the options). ## Adding an agent's accounts

dev-studio's account list is generic over the agent. To give another agent accounts:

- Write one kind file in `bin/lib/account-kinds/` and add it to `KINDS` in `index.ts`. It holds everything
  about the agent's logins; no other file names its folder env or login command. An agent that keeps one login
  sets `multi` to false and says why.
- Put the folder env on that agent's launch line: give the kind its `envVar` and `command(model, effort)`, so a
  start on a non-system account runs that line with the account's folder.
- Test it with a fake agent on `PATH` and a sentinel token in its login file, and check the token never leaves
  that file (not into loop.db, `state/`, the board's data or output). Models: `tests/account-codex.sh`,
  `tests/loop/account-kind-codex.test.ts`. Names and ids in tests are made up.
